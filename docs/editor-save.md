# 编辑器保存策略总览

> 2026-10-17 重构后的现状。目标:打字类编辑不再"一改动就存",服务端场景下每次保存不再引发全应用级联刷新。

## 三类保存策略

| 类别 | 触发时机 | 覆盖的编辑器 |
| --- | --- | --- |
| **自动保存(防抖 + 检查点)** | 停顿 2s 防抖;连续输入 10s 检查点;离开面板冲刷;失焦不触发 | 任务标题、任务正文(tiptap) |
| **单动作即时保存** | 每次点击恰好发一次请求,不做防抖 | 完成勾选、优先级旗标、标签勾选、标签换色、规划页拖拽、回顾启停 |
| **显式提交** | 弹层/表单内本地编辑,点"保存"按钮或提交才发请求 | 安排时间、预计时长、时间段(Plan)、清单(Topic)、结果摘要、材料/记忆、知识实体、回顾规则、交接、资料库重命名、设置 |

单动作即时保存不做防抖是有意为之:勾选/换色是离散动作,不存在"打字中途"的状态,合并反而让 UI 与服务端状态漂移。

## 文字编辑器(标题 + 正文)

唯一"边打字边存"的通道,由应用级 `TaskTextSyncCoordinator`(`client/src/lib/task-text-sync.ts`)统一管理,标题与正文共用一条记录、一套防抖。

### 常量

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `EDIT_DEBOUNCE_MS` | 2000 | 最后一次输入后多久自动保存 |
| `MAX_DIRTY_WAIT_MS` | 10000 | 持续输入不停顿时,强制落检查点的间隔 |
| `PERSIST_THROTTLE_MS` | 250 | 输入期间 IndexedDB 草稿落盘节流(崩溃丢失窗口上限) |
| `NETWORK_WAIT_MS` | 15000 | 单次 PATCH 超时 |
| `RETRY_DELAYS_MS` | 2s / 5s / 15s | 网络/5xx 幂等重试(同一 requestId) |

### 保存时机

标题与正文完全一致（同一条记录、同一个防抖计时，一次 PATCH 同时携带两个字段的变更）：

- **2s 防抖**：最后一次输入后 2 秒自动保存。失焦不触发保存（格式浮条会抢正文焦点，统一不依赖失焦）；标题 Enter 跳正文只是移动焦点，防抖计时继续。
- **10s 检查点**：持续输入不停顿时每 10 秒强制落一次检查点（检查点被确认后等待窗口重开，不会连续补发）。
- **离开详情**：`prepareLeave` 只要求本地 IndexedDB 写入成功，网络同步后台继续；有关闭确认框兜底未保存的 meta 字段。
- **组词保护**：IME composition 期间挂起所有保存，组词结束后重新按防抖计时。
- **本地持久化**：输入至多每 250ms 写一次草稿；发请求前(`runPump`)、离开前会先冲刷挂起的节流写。outbox 写入、冲突处理等状态迁移仍是立即落盘。

### 可靠性机制(未变)

持久化 outbox + 同 requestId 幂等重试;`expectedRevision` 乐观锁,409/412 走字段级三方合并;多窗口分支用 Web Locks 隔离。空标题会以 `invalid-title` 暂停保存。

## 保存引发的失效范围(扇出收敛)

服务端场景延迟的主因曾不是保存频率本身,而是每次保存引发的级联。现行为:

- **SSE 变更事件**(`client/src/hooks/useWorkspaceEvents.ts`):payload 带 `affectedTaskIds` 的任务类事件只失效 `['tasks', 'task', 'changes', 'task-topic-history', 'trash']`;未知/非任务事件回退全量失效。同一突发内的事件按 300ms 合并成一轮(以首个事件起算)。未挂载的 query 失效只标脏、不发请求,因此范围集合偏大也安全。
- **本端任务写入**(`client/src/hooks/useTodo.ts` 的 `invalidationScope`):任务 PATCH 只失效 `['tasks', 'task', 'changes']`;带 topicId/parentId 的结构性变更追加清单相关;创建/删除/回收站/undo 走全量。
- 兜底:30s 轮询、窗口 focus、visibilitychange 仍做全量刷新;版本冲突时全量失效重取。

## 后续可优化项(本次未做)

- 服务端 ChangeRecord 对纯文字保存仍写前后两份全量 JSON 快照(含整段正文),是每次保存最大的写放大来源。
- SSE 自回显抑制:本端刚保存成功后,广播回来的 change 事件仍会触发一轮(已收敛范围的)失效。
