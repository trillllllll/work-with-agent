# Agent 工作室：第一版架构基线

> 修订日期：2026-09-20
>
> 设计顺序：基础 Todo → AI 接入 → 记忆与整理 → Handoff 等增强。
>
> 本文定义后续实施的目标基线；“当前实现”见第 10 节。文档修订不表示对应功能已经实现。

## 1. 产品目标与实施顺序

Work With Agent 首先是一款直觉、易上手、方便修改的个人清单工具。第一阶段参考滴答清单的常用功能和交互，覆盖日常任务管理所需的基础能力；随后让外部 AI 工具访问同一份 Todo 数据，再逐步增加记忆、整理和接力能力。

| 阶段 | 交付目标 | 成立条件 |
|---|---|---|
| 第一阶段：基础 Todo | 收集、组织、编辑和完成任务 | 不配置模型、不连接 AI，也能完整使用这一阶段的清单功能 |
| 第二阶段：AI 接入 | 外部 AI 按授权查询、创建和修改清单与任务 | 用户和 AI 操作同一份数据，修改可见、可追溯、可继续编辑 |
| 第三阶段：记忆与整理 | 关联材料、保留项目经验，辅助整理任务和上下文 | 建立在已有 Todo 和开放接口上，逐项增加 |
| 后续阶段：Handoff 与自动化 | 派发、跟踪、恢复、回收与验收工作 | 复用任务、上下文和连接能力，并增加独立的执行记录 |

各阶段可以独立验收。AI 接入本身就是一个可交付阶段，不以完成记忆系统、内置聊天或自动派发为前提。

本基线确定近期实现顺序；[产品能力设计](./2026-09-20_product-capability-design.md)和两份调研中的 P0/MVP 建议作为中长期能力参考，与此不同的优先级以本文实施顺序为准。核心词义见[领域术语](../CONTEXT.md)。

### 1.1 每个阶段先参考实现，再细化自己的设计

每个阶段开始设计具体功能前，先针对该阶段的问题阅读参考项目的源码和相关测试。功能调研用于选项目；设计依据需要进一步落到具体实现。

1. **限定问题**：例如连续录入如何保留草稿、MCP 如何清空字段、记忆来源变化后怎么办、执行回报重复时怎么办。
2. **选择参考**：每个问题选一到两个主要实现，记录仓库、提交版本、文件和关键符号。
3. **追踪链路**：从输入入口跟到业务处理、数据写入和结果反馈，查看失败路径和有关测试；只读到局部时明确边界。
4. **记录取舍**：分别写明参考项目实际怎么做、我们采纳什么、根据本产品规模如何简化、哪些仍需验证。
5. **再定设计**：把结论补到本阶段接口、数据规则与交互设计；源码没有支撑的选择标记为本产品约定。
6. **实施时验证**：用本产品的真实操作场景和必要测试验证设计，不能把读过测试当作已运行通过。

本轮已完成一轮按阶段的静态源码核对，证据及取舍见[分阶段源码参考与设计取舍](./2026-09-20_stage-source-review.md)。这是一组有范围的设计输入；后续阶段正式实施前，围绕实际功能补读相关路径，并核对参考版本是否变化。

## 2. 第一阶段范围与交互原则

### 2.1 基础 Todo 范围

| 能力 | 第一阶段范围 |
|---|---|
| 任务操作 | 快速创建、编辑标题和说明、勾选完成、重新打开、移动、删除与恢复 |
| 任务组织 | 收集箱、自定义清单、一级子任务、基础标签、手动排序 |
| 时间与优先级 | 可选截止日期、优先级；今天视图展示今日到期任务并单独提示逾期 |
| 查找与浏览 | 列表为默认视图，支持基本搜索和按清单、完成状态、日期、标签筛选 |
| 编辑反馈 | 保存状态明确；可撤销的变更提供撤销入口；删除先进入回收站 |

已有看板可以作为可选视图保留。提醒、重复任务、复杂日历、习惯、番茄钟和多端同步分别按后续需求安排，不作为第一阶段验收条件。

### 2.2 交互原则

1. 创建任务只要求标题；归属、说明、日期、优先级都可以以后补充。
2. 用户可以直接修改任务，保存走普通业务接口，不经过模型或 AI 审批流程。
3. 记录和调整结构同样容易：任务可移入清单、移回收集箱、拆出子任务和调整顺序。
4. 普通任务可以直接勾选完成；进行中、阻塞等状态按需要使用。
5. 清单、今天、搜索结果展示同一个任务；在任意位置修改，其他位置在刷新后反映同一状态。
6. 首屏优先展示收集箱、今天和用户清单。任务详情逐步展示更多信息，AI、材料与记忆功能在对应阶段加入。
7. AI 创建的普通任务遵循相同编辑规则，用户可以继续手动修改。

### 2.3 第一阶段的源码参考与设计落点

参考 Super Productivity 的快速录入状态、提交入口与任务状态更新，以及 Vikunja 的任务修改、跨视图缓存更新与排序实现，具体文件见[源码核对第一阶段](./2026-09-20_stage-source-review.md#stage-1)。

- **快速录入**：把未提交的标题、说明与选择项保留为编辑草稿；中文输入法选字的 Enter 不提交任务，连续按键不重复创建。保存失败保留输入，成功后清空内容并保留当前清单，方便连续录入。
- **编辑反馈**：集中封装任务 mutation 和查询缓存更新，成功回包更新详情与已加载列表，并使筛选结果失效；失败只回滚该次修改涉及的状态。同一任务连续保存时需处理回包顺序，旧响应不能覆盖新编辑。
- **排序范围**：第一阶段手动排序限定在清单根任务和同一父任务的子任务中；今天、标签和搜索先使用确定性排序。排序与任务内容分别修改，后续需要独立视图排序时再扩展。
- **明确简化**：保留 React 与现有服务端；不引入参考项目的 NgRx 操作日志同步或完整多视图浮点排序体系。父子任务完成策略、一级层级和归档语义是本产品约定，实施时用实际场景验证。

## 3. 目标架构与依赖方向

保持现有前后端分离的单体应用，以统一业务用例服务不同入口。

```text
用户                          外部 AI 工具
 ↓                               ↓
清单 / 任务详情 / 搜索         MCP 适配器（第二阶段）
 ↓                            CLI 等适配器（按需）
界面 REST 适配器                  ↓
 └──────────────┬────────────────┘
                ↓
应用层：身份与操作权限、业务用例、变更记录、查询结果
 ├── 调用领域规则：Task、清单/项目、归属、状态与排序
 └── 协调基础设施：Prisma / SQLite、日志、后续文件与检索适配器

可选内置 Agent ── Tool 适配器 ── 同一应用层
后续记忆服务 / Handoff 服务 ─── 同一应用层
```

| 边界 | 职责 |
|---|---|
| 表现层 | 展示清单与任务、收集输入、提供编辑反馈；不拥有另一套任务状态规则 |
| 接口适配层 | 处理 REST、MCP、CLI 或 Tool 的协议输入输出，将调用转换为业务请求 |
| 应用层 | 校验调用范围，协调领域规则、持久化、审批与变更记录，返回明确结果 |
| 领域层 | 维护任务完成、归属、子任务关系和清单生命周期等业务规则，不依赖模型或协议 |
| 基础设施层 | 提供存储、日志和可选的模型、文件、检索、执行能力 |

REST 与 AI 工具复用业务用例和字段校验约束；接口层可以使用适合各自协议的输入格式。AI 只能通过开放接口操作数据，不能直接写数据库。AI 接入层不保存独立的任务副本。

现有 React、TypeScript、Express、Prisma 与 SQLite 继续作为实现基础。模型调用、上下文压缩、记忆检索和执行环境保持可选，普通 Todo 用例不依赖它们。

## 4. 核心对象与业务规则

### 4.1 Task、清单与项目

| 对象 | 第一阶段含义 | 后续扩展方向 |
|---|---|---|
| Task | 用户需要处理的工作项，具有稳定标识、标题、说明、完成状态、可选日期与优先级 | 关联材料、记忆、执行记录和成果 |
| 清单 | 组织任务的容器，创建时只需名称 | 长期工作的清单可逐步补充项目目标和上下文 |
| 收集箱 | 尚未归入清单的任务集合 | 后续可接收更多待整理输入 |
| 子任务 | 属于一个父任务的任务，第一阶段仅支持一级 | 按实际需求扩展依赖关系 |
| 标签 | 可复用的分类标记，一个任务可关联多个标签 | 用于更丰富的筛选视图 |
| 视图 | 按条件和顺序展示任务的查询结果 | 保存筛选条件形成智能清单 |
| ChangeRecord | 一次变更的主体、来源、前后内容与时间 | 为撤销、AI 操作追踪和后续项目历史提供基础 |

现有 `Topic` 同时承载任务分组和探索主题。第一阶段沿用其已有数据与 ID，前台以清单操作为主；长期项目能力在此基础上逐步增加。暂不要求用户同时维护“清单、主题、项目”三套平行结构，也不因前台改名立即重命名数据库表与既有 API。

一个任务只有一个主要归属；没有归属时进入收集箱。同一任务可以出现在今天、标签和搜索等多个视图里，这不会改变其归属或产生副本。目标尚不明确的清单可以保留探索性质，目标、阶段和完成标准都不是创建的必填项。

### 4.2 完成、子任务与日期

- 新任务默认为 `todo`；普通任务支持 `todo → done` 和 `done → todo`，不要求先进入 `doing`。
- 为兼容已有任务，保留 `doing`、`blocked` 的表达能力及原有可用转换；两者也可以直接完成。取消完成统一回到 `todo`，需要恢复其他状态时另行修改。
- 子任务有独立 ID 和完成状态，与父任务同属一个清单；禁止循环关系和超过一级的嵌套。移动父任务时子任务跟随归属；单独把子任务移到其他清单时需解除父子关系。
- 父任务删除与恢复应覆盖本次操作涉及的子任务并作为一组记录，不恢复之前已单独删除的子任务。完成父任务时，有未完成子任务则由用户选择一并完成或保留父任务未完成；全部子任务完成后，父任务仍由用户决定完成。重新打开子任务时，已完成的父任务一并重新打开并记录变更。
- 手动排序需要显式保存顺序；编辑标题或说明不应意外改变手动排序。按日期或优先级浏览属于独立的排序方式。
- 第一阶段截止日期使用用户本地日历日期 `YYYY-MM-DD`，不把纯日期隐式转换成 UTC 时间点。具体时刻、提醒与重复规则后续单独设计。

上述状态与子任务规则是目标设计；现有状态机的差异见第 10 节。

### 4.3 删除、归档与撤销

- 任务删除先进入回收站，恢复时保留原内容和可用的归属；原清单不可用时回到收集箱，并说明原因。
- 清单归档的目标语义是隐藏日常工作项并保留任务及归属，便于以后恢复。“将任务移入收集箱”作为单独的显式操作，避免归档时失去整理结构。
- 旧主题删除接口会归档主题并把任务移入收集箱；第一阶段新增独立归档接口保留归属，新界面使用新接口。旧接口与历史 `archive` 记录继续保持原语义。
- 撤销生成一条新的变更记录，不删除历史；若对象已有后续修改，返回冲突并让用户选择，不能用旧快照覆盖新内容。
- 永久删除需明确操作范围，不承诺可撤销。外部副作用与本地数据撤销分开处理。

## 5. 第二阶段：让外部 AI 访问 Todo

### 5.1 交付边界

外部 AI 可以在用户授权范围内查询清单、读取任务、创建任务、修改字段、完成任务并写回说明或结果链接。用户在 AI 工具中操作后，可以回到本产品查看和继续编辑同一个任务。

优先实现 MCP 适配器；CLI 等入口按接入需要补充，复用相同业务能力。提供连接配置、可用能力说明和简短使用约定，让 AI 知道如何查找对象、读取详情、处理错误和写回结果。自动会话捕获与生命周期 hooks 后续按宿主能力加入。

连接外部 AI 不要求用户先在本产品配置模型。模型推理由外部工具负责；现有内置 Agent 可以继续作为另一种可选入口。

### 5.2 最小能力契约

以下是能力分组，具体工具名在接口实施时确定：

| 能力 | 输入与输出要求 |
|---|---|
| 发现与查询 | 列出可访问清单，按归属、状态、日期、关键词查询任务；返回稳定 ID、摘要和分页信息 |
| 详情读取 | 按 ID 读取任务、父子关系和所属清单；关联内容按需读取 |
| 创建与编辑 | 创建任务，局部修改字段，调整归属、子任务与顺序；未提供保持原值，可空字段用 `null` 清空，集合用 `[]` 清空，`false` 和 `0` 按字段规则保留，空字符串按字段含义校验 |
| 完成与恢复 | 使用和界面相同的完成、重新打开、回收站恢复语义 |
| 写回结果 | 更新任务说明或结果字段，并关联链接；首次接入不要求保存完整 AI 会话 |
| 变更反馈 | 返回已执行、待确认、无权限、冲突或失败，附相关对象标识与可用的变更标识 |

先查找再读取详情，避免默认传输整个项目或全部历史。清单和任务的普通查询可以由确定性数据库查询完成，语义检索作为后续增强。

### 5.3 共同数据与修改契约

1. 每个任务和清单保持稳定 ID；改名、移动与切换 AI 工具不会更换对象身份。
2. 所有入口复用业务规则；最终状态由应用用例和领域模型维护。
3. 所有入口更新已有对象时携带预期版本，服务端检查并发修改；外部写请求另带请求标识，创建新对象不要求已有版本。相同请求的重试返回原处理结果；相同请求标识对应不同内容时拒绝执行。具体版本与幂等存储在第二阶段完善。
4. 数据修改与变更记录在同一事务中提交；记录调用主体、连接来源、操作范围及前后内容。待确认的提议与已执行的变更分别记录。
5. 返回成功前确保数据已保存。界面重新进入或刷新时读取最新数据；活跃页面通过缓存失效、轮询或事件通知及时更新，具体机制实施时选择。
6. UI 的乐观更新失败时恢复显示并提示原因。待确认、失败或冲突不能显示为已完成。

### 5.4 第二阶段的源码参考与设计落点

参考 Pith 的任务 MCP 与 HTTP 业务调用、Plane MCP 的工作范围和分页封装、Nowledge Community 的公开连接器，见[源码核对第二阶段](./2026-09-20_stage-source-review.md#stage-2)。

- MCP、CLI 与内置 Tool 保持薄适配：处理协议与字段映射，复用本产品应用用例，避免复制任务规则。
- 同进程适配器直接调用应用用例；独立进程适配器通过受认证的 HTTP 客户端访问用例入口。部署方式在第二阶段用首个宿主验证后确定；标签集合、子任务归属和排序等组合修改由用例维护一致性，适配器不自行读取后合并覆盖。
- 为未提供、显式清空、布尔值和集合建立共同的契约样例；适配器不能把所有假值转换为“没有输入”。
- 查询结果保留分页与截断信息；业务错误保留错误码、对象标识和可重试性，不能统一降成一段无法判断状态的文本。
- 连接器、使用说明和后续 hooks 分层。工具使用说明负责指导调用时机，服务端负责实际权限；安装了说明不代表已经建立连接或获得写权限。
- Nowledge Mem 本轮只核对公开连接器，未读到核心存储与检索的实现，不将这部分作为已验证的实现依据。多入口版本校验和幂等仍由本产品实现并测试。

## 6. 用户控制、授权与审批

用户在界面里直接编辑，与 AI 提出或执行修改，使用不同的授权入口，但最终调用同一业务用例。

| 操作 | 目标处理方式 |
|---|---|
| 用户直接创建、编辑、完成任务 | 保存并记录变更；可撤销操作提供撤销入口 |
| AI 读取信息 | 校验连接身份和可访问范围，在范围内直接读取 |
| AI 修改普通 Todo 数据 | 默认生成待确认修改；用户可显式授权某连接在指定清单中执行指定的可撤销操作，授权范围内直接执行并记录 |
| AI 操作超出已有授权 | 返回无权限或待确认，不因调用协议改变而获得额外权限 |
| AI 永久删除或执行外部副作用 | 单独审核具体操作，不包含在普通 Todo 写权限中 |

外部调用主体与权限由服务端从连接凭证确定，不能相信请求自行声明的 `source: user`。面向 AI 的 MCP、CLI 和 REST 入口采用一致的权限边界，不能通过界面 REST 绕过检查。

用户需要确认时，展示具体业务改动，例如“创建三条子任务、修改截止日期”，允许调整后确认。一次用户意图可以形成一组修改；每项仍保留执行记录。组内依赖修改采用事务，独立项目若分批执行则逐项报告结果。确认时重新校验版本，过期提议不能覆盖后来编辑的任务。

这是第二阶段的目标策略。现有内置 Agent 的逐工具审批继续保留，直到新的连接授权与业务修改预览实现并验收；本次文档修订不直接放宽现有工具执行权限。

## 7. 三条运行链路

### 7.1 用户管理任务

```text
输入 / 编辑 / 勾选
  → 界面 REST 接口
  → 业务校验与状态更新
  → 持久化 + 变更记录
  → 更新界面 / 提供撤销
```

### 7.2 外部 AI 操作任务

```text
用户在外部 AI 工具中提出要求
  → AI 查询清单与任务，按需读取详情
  → MCP 等接口校验身份与操作范围
  → 已授权则执行，需确认则保存提议并返回待确认
  → 同一业务用例保存变更，返回实际执行结果
  → 用户在清单界面查看并继续修改
```

### 7.3 后续记忆与接力

```text
任务 + 材料 + 执行结果
  → 提炼并确认项目记忆
  → 按任务组装需要的上下文
  → 准备交接内容，需要派发时创建 Run
  → 接收并验收结果，再更新任务或提议新的项目记忆
```

## 8. 记忆、整理与 Handoff 的扩展边界

第三阶段以后逐步引入以下对象，不要求在第一阶段预先建全表或展示全部入口：

| 能力 | 负责什么 | 与 Todo 的关系 |
|---|---|---|
| Material / Thread | 保存材料和原始会话，标记来源及关联对象 | 为任务与项目提供原始依据 |
| Memory | 保存有来源的事实、决策、约束和经验，记录确认、替代与冲突 | 补充任务背景，不能取代任务的实时状态 |
| Working Memory | 从近期任务、变化和有效记忆生成短小工作摘要 | 是可重建的阅读视图；修改摘要不会隐式修改底层任务 |
| 整理建议 | 提出归类、拆分、关联与内容修订 | 复用已有任务操作和修改确认机制 |
| 交接内容 | 本次要做的工作、要求、上下文引用与输入版本 | 可以先导出，也可以作为执行输入 |
| Run | 记录一次执行的接收、启动、状态、外部标识、结果和重试来源 | 一个任务可以有多次执行，执行状态与任务状态分开 |
| 结果接收与验收 | 记录已收回的结果及用户是否采纳、确认完成 | 验收后通过既有 Todo 用例修改任务 |
| Artifact | 保存任务产物的描述、引用与来源 | 可以成为后续任务的输入 |

原始材料、提炼后的记忆、一次使用的上下文包分别保存或生成。原始会话与接力摘要明确区分；只有实际获得完整会话时才标记为完整记录。

AI 能访问 Todo 后，整理和接力可复用开放接口；正式 Handoff 仍需补充派发、恢复、状态同步和结果验收。AI 已回复表示一次执行有返回，不能直接等同于用户任务已完成。

### 8.1 第三阶段的源码参考与设计落点

参考 projectmem 的追加事件与摘要重建、MemoryWiki 的来源摄取、候选确认与索引校验，见[源码核对第三阶段](./2026-09-20_stage-source-review.md#stage-3)。

- 先提供材料关联和人工可编辑的项目记忆，再增加 AI 提炼候选。候选记录来源对象、来源版本或内容 hash、作用范围和生成来源；确认时检查来源与目标是否已变化。
- 候选、当前有效记忆、已被替代的历史分别表达。普通上下文装配默认读取有效记忆；历史和冲突内容通过明确的查询入口提供，并附状态与来源。
- 记忆修订保留旧版本及替代理由。Working Memory 和检索索引保存生成依据，可以重建；索引更新失败时应回退原数据或提示未更新，不把旧索引当作最新状态。
- 参考实现中的英文规则提取、固定置信度和 token 哈希向量，不作为中文语义理解或事实确认的质量证明。第三阶段需用本项目材料验证候选准确性与召回质量。

### 8.2 Handoff 阶段的源码参考与设计落点

参考 Multica 的 Issue 与执行队列分离、CCB 的 job/session 映射与恢复处理，见[源码核对后续阶段](./2026-09-20_stage-source-review.md#stage-4)。

- 每次执行具有独立 Run ID，关联本产品 Task ID 和外部 provider/job/session ID；重新执行产生新 Run，保留原执行结果与失败原因。
- 派发已接受、正在执行、等待输入、已返回和已验收分别表达。运行超时或失联表示观察状态异常，不自动推断外部工作已取消或任务已完成。
- 接收回报时核对 Run 与外部标识，处理重复和晚到消息；结束状态的回报不重复应用任务变更或重复验收。
- 每个执行适配器明确是否支持恢复会话、查询状态、取消和结果补收。不能恢复时保留失败记录并允许重新提交，不把恢复连接当作恢复执行。
- 具体派发协议和状态机在该阶段实现前补充，不在基础 Todo 阶段复制完整 Agent 调度平台。

## 9. 可选内置 Agent 与受控执行

内置聊天作为辅助入口，默认携带当前页面、当前对象和少量近期上下文；更广的信息通过查询接口按需获取。上下文压缩属于会话能力，不承担项目记忆的职责。

现有受控 Shell、HTTP 和文件工具继续放在执行适配器中，并保留原有边界：

- 执行请求先生成 Approval，再由服务端适配器处理。
- Shell 使用白名单命令、参数数组、受控工作目录、超时和输出上限。
- 文件访问限制在工作区根目录，拒绝路径穿越和工作区外访问。
- HTTP 仅允许 HTTP(S)，默认阻止回环、内网、云元数据和本地解析地址。
- 执行结果与审核关联记录；外部副作用不承诺支持工作区撤销。

这些工具不属于基础 Todo 的依赖，也不因开放 Todo MCP 接口而自动开放给外部 AI。是否增加其他执行环境或接入 CCB 等运行时，在 Handoff 阶段决定。

## 11. 分阶段验收与工程命令

### 11.1 行为验收

- **第一阶段**：不配置模型即可创建清单和任务；仅标题可以保存；任务可以直接完成并重新打开；日期、优先级、标签、归属和顺序可修改；父子任务操作符合第 4 节；删除后可恢复，撤销不覆盖后续变更；今天和搜索视图与任务详情一致。
- **第二阶段**：至少接通一种外部 AI 工具。用户创建的任务可被查询；AI 在授权范围内修改后，用户能在界面看到并继续编辑；越权请求被拒绝；待确认与执行成功有明确区别；重复请求不会重复创建，冲突不会静默覆盖；不需要先配置内置模型或建好记忆系统。
- **后续阶段**：材料与记忆来源可追溯；摘要与原始数据分开；接力结果能回到对应任务；执行完成与任务验收分别记录。

### 11.2 本地验收命令

- `npm test`：运行服务端和客户端单元/集成测试。
- `npm run build`：构建服务端和客户端。为避免 Windows 下运行中的 Prisma DLL 文件锁，根构建不会自动重新生成 Prisma Client；修改 Schema 后先显式运行 `npm run prisma:generate`。
- `npm run e2e`：先显式生成 Prisma Client，再使用独立 SQLite 数据库和本地 Mock 模型服务运行 Chromium 桌面/移动端验收。测试数据库会在每条用例前清空，不会复用开发数据。
- `npm run e2e:real`：仅在设置 `E2E_REAL_MODEL=1`、`E2E_MODEL_BASE_URL`、`E2E_MODEL_API_KEY` 和 `E2E_MODEL_NAME` 后运行真实模型冒烟测试。
- `npm run test:all`：依次运行单元/集成测试和默认 Mock E2E 验收。

CI 会显式运行 `npm run prisma:generate`。本地开发服务器运行期间不要重复生成 Prisma Client；如修改了 `server/prisma/schema.prisma`，应先停止服务、执行生成和 `npm run db:migrate`，再重新启动服务。

仅修改本文时检查文档结构、链接与差异；实现对应功能时再运行相关领域、接口与界面测试。模型调用失败不应影响基础 Todo 的验收。

源码参考补充的场景也纳入对应阶段验收：第一阶段检查中文输入、连续录入、保存失败和多视图更新；第二阶段检查分页、显式清空、权限、重复请求和冲突；第三阶段检查来源过期、决策替代与索引更新失败；Handoff 阶段检查重复回报、晚到回报和无法恢复的执行。
