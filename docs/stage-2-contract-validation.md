# 第二阶段共同命令与身份契约验收

记录日期：2026-09-21。范围为 2A 身份、共同命令、提议、幂等、版本与旧接口兼容。完整迁移、前端、MCP 双宿主和后续阶段验收由总实施记录补充。

## 已实现契约

- 浏览器使用启动时生成的一次性凭据换取 `HttpOnly` 会话；写入需同时通过 Origin、主机名和 CSRF 检查。外部连接使用独立 Bearer 凭据，不能调用旧 `/api/*` 用户入口。
- `/api/v1/commands` 接受 `requestId` 和最多 50 条命令。已有对象修改携带 `expectedRevision`；排序同时携带范围全部成员的 `expectedRevisions`。字段省略、`null` 与空数组语义沿用第一阶段。
- 默认外部写入与内置模型写入产生 `pending_approval`。提议保留原身份、授权版本、对象及关系读集合；确认前重新校验，整个批次与回执在同一数据库事务中提交。
- 回执键为 `(actorId, requestId)`；相同请求返回原响应，不同内容返回幂等冲突。重放还需通过当前授权和对象范围检查。
- 级联用户操作先返回 `PREVIEW_REQUIRED` 及原命令；预览 token 绑定命令、身份、授权版本和完整读集合。提交不能以新读取的目标版本替换用户原先提交的版本。
- 旧 REST 仍返回原来的 `data`、`meta` 包装，但其写入已映射到共同命令。内置新审批不能静默补读目标版本。旧无快照审批需先调用明确的预览接口，再确认。
- 每个批次形成一条分组审计，保留 actor、connection、proposal 及兼容的 approval/conversation 归因。跨任务撤销先验证整组对象与关系，冲突时全部拒绝。

## 最后只读审查发现

发现并修复一个自动授权边界缺口：仅授予 `task.create` 的连接创建未完成子任务时，原实现可能隐式重开已完成父任务。提交时原先只对用户身份强制级联预览，连接自动执行门槛未包含这项父任务状态变更，且父版本参数原为可选。

最终采用严格策略：连接凡涉及相关任务的级联效果，一律生成待确认提议，即使有自动授权和合法预览 token 也不能直接执行。用户确认时重新校验父任务版本和完整关系集合。第 11 项回归覆盖子任务创建、提议后的父任务变化与父子批量完成。该 P1 已关闭。

随后审查发现第二个 P1：前端编辑器发回的是服务端已解析依赖的规范化命令；编辑时重新生成所有创建 ID，会让子任务父 ID 或记忆来源 ID 仍指向旧值，导致有效提议无法确认。现仅在编辑入口接受返回的 `entityId`，并与当前提议数据库中的原创建命令及对象类型核对；新增创建仍由服务端生成 ID，旧客户端也可按原 `clientRef` 识别可信创建。归一化校验重复 ID、已删除对象的悬空依赖和循环，并按创建依赖进行稳定排序。第 12 至 14 项覆盖父子和材料记忆场景及伪造输入，该 P1 已关闭。

未发现可通过 HTTP 伪造用户身份、内置工具自行确认提议、旧 REST 绕过认证，或命令预览触发受控执行的其他 P0/P1 问题。知识附件预览遵循 `context.preview`，不会写入受管附件文件。
