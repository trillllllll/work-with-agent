# Dovun 0.4.0 完成版候选与身份迁移

本分支独立于 0.3.0 过渡版。0.3.0 的完整兼容代码保留在 `codex/dovun-workspace`；本分支为 `codex/dovun-0.4`。没有安装、部署、改仓库或切域名。

## 当前实现

- 系统标识为 `app.dovun.desktop`；工程包、进程、默认目录、数据库和 MCP 启动器均使用 Dovun。
- 只读取 `DOVUN_*`。检测到只有旧 `WWA_*` 配置时，在启动前停止并列出键名，要求先盘点原数据和更新原配置；不把旧值当作新设置，也不输出值。旧自定义目录不能因此被静默丢开。
- 移除旧桌面哨兵、事件桥、语言头、会话 cookie 读取和 MCP 启动别名。已有宿主中的原条目继续原位更新，不能因为默认名为 dovun 而新增第二条。
- 原数据导入、旧快照和正文资料链接解析保留。REST 路径、MCP 工具、ID 和业务表结构不改。新目录中的受管理 `wwa-mcp` 别名退役，旧来源和备份仍保留作恢复材料。

## 首次窗口前恢复

Tauri 默认窗口设置 `create:false`。setup 先调用打包 Node 的 `profile-migrate.js`，成功后才手动创建唯一主 WebView。失败用非阻塞原生对话框显示错误，确认后退出；不创建空的新浏览器工作区。

macOS 复制 `~/Library/WebKit/<旧标识>` 与 `~/Library/Application Support/<旧标识>` 两棵原生状态树到新标识；包含 origin salt、LocalStorage、IndexedDB、cookie 和窗口状态。Windows 复制 `%LOCALAPPDATA%/<旧标识>` 整棵 WebView2 状态树。路径选择依据当前 Tauri/Wry 源码；并在本机只核对过旧目录结构，没有读取真实用户正文。

旧应用须完全退出。工具使用独立互斥，先完整备份、逐文件 SHA256 校验，再复制到临时目录；再次检查旧进程和来源摘要后原子切换。每棵树有迁移凭证，重复启动不会覆盖新状态。新旧 profile 都有状态且没有匹配凭证时停止，由使用者备份后明确选择。中途失败保留来源和备份，下一次可重试；不自动合并两个 profile。

复制完成后，客户端在挂载前迁移旧偏好键与草稿数据库。因此经过 0.3.0 与直接来自 0.2 的来源都走同一入口，保留 origin、服务、用户和草稿分支。登录失效时需要重新登录，不能把保留旧聊天状态等同于保留有效的登录权限。

## 数据与执行端

桌面默认旧目录仍经过停服、备份、完整复制和核对，详见 [目录迁移手册](dovun-migration.md)。自定义目录需先离线迁移，再设置 `DOVUN_DATA_DIR`。容器发现旧默认数据库而未指定来源时停止，先在停服状态下迁移到单独的新目录，再更新挂载；不能只改环境变量后删除旧库。显式 `DATABASE_URL` 仍是业务数据库定位配置，不批量修改用户路径。

独立 CLI 执行端发现 `.wwa-node` 时不静默建立空的新执行端；停止旧端后，明确使用 `--data <原目录>` 或先离线迁移。桌面托管执行端的 `node/` 已随完整数据目录迁移。

## 验证方法与范围

- 单元测试覆盖 profile 完整备份/复制、冲突、中断、来源变化、重复执行、macOS/Windows 路径；原生测试覆盖过期自定义目录的启动阻断。
- `node scripts/profile-migration-smoke.mjs` 使用两个可丢弃的真实 WebKit persistent profiles，分别模拟 0.2 与 0.3。关闭旧引擎后完整复制，重新打开新 profile，核对 cookie、主题、聊天恢复状态、带 origin/用户/服务范围的 IndexedDB 草稿及清除 pending 不复活。它不会打开已安装的应用，也不会使用真实用户 profile。
- macOS 候选包标识和版本由实际 Info.plist 核对；打包服务另做本机/服务器模式与 MCP 重启恢复冒烟。WebKit 引擎恢复证据不能当作 Windows 原生安装验收。
- Windows WebView2 的原生升级仍需在 Windows 机器执行；本轮没有该运行环境。真实用户目录和已安装应用未作为实验对象。实际安装、公网验收和数据核对仍属于后续切换步骤。

最终检查记录会补到 [交付记录](design/dovun/implementation/delivery.md)，不把源码完成、引擎隔离验证、候选包构建和实际发布混成一个状态。
